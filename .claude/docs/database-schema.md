# Database schema & types

_Feature deep-dive extracted from `CLAUDE.md`. That file holds the repo-wide conventions, commands and verification gate; this one holds only the migration history and the RLS model._

- Schema is built from migrations in `supabase/migrations/`, applied **in order** via the Supabase SQL Editor or `supabase db push` (see README). **Several features were built then removed** — their create + drop migrations are kept as historical record, not live schema: Instagram Leads CRM (`0005`/`0020`), Social Hub (`0006`/`0011`), and Bio Pages (`0012`–`0014`). Skip past them unless you're tracing that history.
  - `0001_initial_schema.sql` — `clients`, `invoices`, `invoice_items`, `payments`, `company_settings`; the `TD-INV-####` numbering sequence and total-calculation triggers.
  - `0002_auth_and_owner_scoping.sql` — adds `owner_id` to every table and **tightens RLS to `auth.uid()`** (no more permissive anon access).
  - `0003_client_portal.sql` — `client_users`, `client_file_folders`, `client_files`, `file_activity`; additive portal-scoped `SELECT` policies (via `portal_client_id()`) with admin write policies preserved.
  - `0004_client_files_storage.sql` — creates the **private `client-files` Storage bucket** and `storage.objects` policies mirroring the table policies.
  - `0005_instagram_leads.sql` — (removed) created the Instagram Leads CRM `leads` table; dropped again by `0020`. Kept only as historical record.
  - `0006_social_hub.sql` — (removed) created the dormant Instagram Social Hub tables; dropped again by `0011`. Kept only as historical record.
  - `0007_qr_codes.sql` — owner-scoped `qr_codes` (saved/dynamic QR codes) plus the `SECURITY DEFINER` `resolve_qr_slug()` helper for the anonymous redirect (superseded in 0008).
  - `0008_qr_scans.sql` — append-only `qr_scans` analytics, the `qr_code_scan_counts` (`security_invoker`) view, and the `SECURITY DEFINER` `resolve_qr_target()` / `log_qr_scan()` helpers that the public `/q/<slug>` route uses.
  - `0009_profiles.sql` — customer self-signup `profiles` (owner-only RLS, no role column). See **Auth & roles**.
  - `0010_qr_generations.sql` — append-only `qr_generations` history (every code generated, admin + anonymous public). RLS exposes nothing to normal clients; inserts go through the `SECURITY DEFINER` `log_qr_generation()` (owner_id from JWT, null when anonymous), admin reads via the service-role client.
  - `0011_drop_social_hub.sql` — drops the `social_accounts` / `social_posts` / `social_sync_logs` tables; the Social Hub was removed entirely.
  - `0012_bio_pages.sql` / `0013_bio_page_styles.sql` — (removed) created the Bio Pages (link-in-bio) builder: `bio_pages`/`bio_links`/`bio_page_views`, the public `get_bio_page()`/`get_bio_links()`/`log_bio_page_view()` helpers, and the `bio-page-assets` Storage bucket. Dropped again by `0014`. Kept only as historical record.
  - `0014_drop_bio_pages.sql` — drops the `bio_pages` / `bio_links` / `bio_page_views` tables, the bio RPCs, and the `bio-page-assets` bucket; the Bio Pages feature was removed entirely.
  - `0015_cutline_files.sql` — created the **private `cutline-files` Storage bucket** for an earlier (admin, stored) version of the Cutline Generator. **Now unused:** the Cutline Generator was made public and storageless (composes PDFs in-request and streams them back — see **Cutline Generator**), so this bucket is no longer written to. Left in place because hosted Supabase blocks deleting buckets via SQL; remove it via the Dashboard/Storage API if you want it gone.
  - `0016_client_projects.sql` — the **client-projects** layer over the portal (see **Client portals & secure file storage**): `project_status` enum + owner-scoped `client_projects` table; adds `client_files.project_id` / `archived_at` / `display_order` and `client_users.must_change_password`; portal SELECT policies hiding draft/archived projects and archived files (and files of hidden projects); the `SECURITY DEFINER` `clear_must_change_password()` RPC (a user clears only their own flag — an UPDATE policy would leak `can_upload`); and sets the `client-files` bucket `file_size_limit` to 25 MB for the new direct-to-Storage upload path.
  - `0017_portal_write_hardening.sql` — **security fix** for a latent gap in the `0003` portal `*_admin_all` policies: they gated writes only on `owner_id = auth.uid()` (the column default), so any authenticated user could INSERT self-owned rows into `client_users`/`client_file_folders`/`client_files`/`client_projects` — worst case, mapping their own auth user to another client's portal. Now every `*_admin_all` policy (and the `file_activity` insert policy) additionally requires the caller to **own the referenced `clients` row** (the check `0004`'s storage policies always made). Admins pass; portal users and self-signup customers don't. Caught by the feature's RLS verification probes.
  - `0018_portal_storage_hide_archived.sql` — **security fix** closing the Storage-layer half of the `0016` archival guarantee: the `client_files_portal_select` policy on `storage.objects` (from `0004`) still granted portal users a coarse "first path segment == your client id" read, so archived files / files of draft-or-archived projects — hidden by the *table* RLS — could still be listed and fetched directly from Storage. The policy now requires a portal-**visible** `client_files` row for the exact object key (same predicate as the table policy). Admin storage access and the portal upload policy are untouched.
  - `0019_portal_dam.sql` — the portal file-browser layer: per-user `client_file_favorites` (RLS: own rows only, and only for files the caller can already see) and the portal SELECT policy on `file_activity` (timeline).
  - `0020_drop_instagram_leads.sql` — drops the `leads` table; the Instagram Leads CRM (`/leads`) was removed entirely. (The later `/martyig` page is **unrelated** — static JSON, no DB.)
  - `0021_design_requests_bucket.sql` — the private `design-requests` bucket backing file uploads on the public custom-design-request form (no policies; service-role only — see the form's entry under Routes).
  - `0022_tasks.sql` — the admin **task manager** that now IS the `/dashboard`: `task_status`/`task_priority` enums and the owner-scoped `tasks` table (optional `client_id` link whose `with check` verifies the client is the caller's own). Invoice stat cards + recent invoices moved to `/invoices`. Domain helpers in `lib/tasks.ts` (labels, `sortTasks()`, overdue/due-today), reads via `getTasks()` in `lib/data.ts`, writes in `app/actions/tasks.ts`, UI in `components/dashboard/task-manager.tsx` (quick-add, toggle-done, edit dialog, delete).
  - `0023_mylar_printing_inquiries.sql` — the public **Custom Mylar Printing** quote wizard: the `mylar_printing_inquiries` table plus the private `mylar-artwork` bucket (50 MB cap). Along with `0024`'s two child tables, these are **the only tables in this schema with no `owner_id`** — inquiries are filed by anonymous visitors, so they follow the `qr_generations` model instead: RLS on with **no policies**, reachable only through the service-role client (validated server action in, `requireAdmin()`-guarded dashboard out). Its flat `front_artwork_*` / `back_artwork_*` columns are superseded by `0024` — still present, no longer written. See **Custom Mylar Printing**.
  - `0024_mylar_designs.sql` — **multi-design mylar orders**: `mylar_designs` (one row per design, carrying its slice of the order quantity) and its child `mylar_artwork_files` (one row per uploaded file, `side` a widenable `check` rather than an enum). Non-destructive — every existing inquiry was backfilled into exactly one fully-allocated design, and the legacy artwork columns were left in place for a release; the migration's trailing comment holds both verification queries and the eventual `drop column` statement. RLS on, no policies, same as `0023`.
  - `0025_mylar_lead_details.sql` — **lead detail fields** on `mylar_printing_inquiries`: `brand_name`, `contact_method` (`text`/`call`/`email`, widenable `check` not an enum), and `needed_by` (`date`). Purely additive, and **all three nullable on purpose** — inquiries filed before the questions existed stated nothing, so null means "not stated" and the admin view renders "—" rather than a defaulted guess. The wizard requires `contact_method` going forward; that rule lives in the submission schema, not the column. Adding columns grants nothing to anon (there is no policy to widen), so the service-role-only access model is unchanged. **Does not touch the legacy `front_artwork_*` columns** — that drop is still pending, see `0024`.
  - **The numbering scheme changed here.** Everything above is hand-numbered `NNNN_`; everything below is a Supabase CLI timestamp (`supabase migration new`). Both live in the same folder and still apply in filename order — keep adding timestamped files rather than continuing the `00NN` series.
  - `20260822182058_custom_design_requests.sql` — durable intake for the public custom-design form (see **Custom design requests**): `custom_design_requests` + child `custom_design_request_files`. Like the mylar tables it has **no `owner_id`** and **RLS on with no policies**, and it goes one step further — it explicitly `revoke all ... from anon, authenticated` on both tables, defense in depth for projects whose `public` schema is exposed through the Data API. Statuses (`new`→`reviewing`→`quoted`→`in_progress`→`completed`/`cancelled`), the `DES-XXXXXX` reference format, and the field limits are **`check` constraints, not enums** — widen them in SQL and in `lib/design-requests/types.ts` together.
  - `20260822230058_premade_designs_manifest.sql` — the `SECURITY DEFINER` `list_premade_design_paths()` RPC behind `/premadedesigns`: one manifest read replacing ~95 Storage folder-list calls. It returns **filenames only** — bytes still need signed URLs minted after the keypad gate. `SECURITY DEFINER` functions get `EXECUTE` for `PUBLIC` by default, so it deliberately revokes that and grants **`service_role` only**; do not widen it to `anon`.
  - `20260824022608_one_active_portal_login_per_client.sql` — a partial unique index, `client_users (client_id) where revoked_at is null`, making **one active portal login per client** a database invariant instead of an application assumption. `user_id` being UNIQUE since `0003` only ever guaranteed the other direction (one portal per person); two approvals racing for the same *client* differ in `user_id`, so they never collided and both won. Both writers are covered — `approvePortalAccessAction` and `createPortalUserAction` — and both now tell the two constraints apart **by name** rather than treating every `23505` alike (see `ONE_PER_USER` / `ONE_PER_CLIENT` in `app/actions/portal.ts`): losing on `user_id` is an idempotent re-approval and reports success, losing on `client_id` is a real collision and must not. Nothing un-revokes a row in place, so the index can never block a restore. **Written but not applied** — verified read-only against production first (0 clients with more than one active login).
  - `20260824193000_workspace_admin_ownership.sql` — **multi-admin workspace ownership**: the `workspace_admins` / `workspace_owner` tables, the `current_owner_id()` helper, the mutual-exclusion trigger pair, and a rewrite of every owner-scoped policy (core tables, portal layer, `file_activity`, QR, tasks, favorites, and the `client-files` storage policy) from `auth.uid()` to `current_owner_id()`. Additive and behavior-preserving for a single admin — with `workspace_owner` empty the helper falls back to `auth.uid()`. See **Workspace admin ownership** for what it does and does not remap; **read that section before touching any owner-scoped policy.**
  - `20260825120000_partner_job_portal.sql` — the **print-partner job portal** (see that section): `partner_companies` / `partner_users` / `design_jobs` / `design_job_items` / `design_job_files`, the `partner_company_id()` / `is_partner_user()` membership helpers, the per-company job-number trigger, the transactional `create_design_job()` RPC, and the private `partner-job-files` bucket with real per-company storage policies. Purely additive — it touches no existing table, policy or bucket, and depends on nothing from `20260824193000`. Seeds the Zaza company; the first rep's `partner_users` row is a manual step (see README).
  - `20260826000000_partner_job_editing.sql` — **lets reps edit and delete their own jobs**, reversing the "a filed job is a record" stance of `20260825120000`. Adds UPDATE + DELETE policies on `design_jobs`/`design_job_items`/`design_job_files` (all scoped by `partner_company_id()`, so the company boundary is unchanged — only the verbs widened), a Storage DELETE policy on the `partner-job-files` prefix, and the transactional `update_design_job()` RPC. **The "a rep cannot change status" invariant moved from policy absence to a trigger**: `protect_design_job_columns()` forces `status`/`company_id`/`job_number`/`submitted_by`/`created_at` back to their previous values for any caller with an `auth.uid()`. RLS `with check` cannot see the OLD row, so "any column but this one" is not expressible as a policy; the service role has no `auth.uid()`, so the admin status write is unaffected. **`status` was removed from that forced-back set by `20260831113855`** — read that entry before reasoning about who may write it; the trigger's other four columns are still immutable to reps.
  - `20260826140000_partner_jar_250ml.sql` — adds `jar_250ml` to the `design_job_items.product_type` check constraint. One statement, purely additive, and the worked example of why that list is a **`check` rather than a pg enum**: it widens inside a transaction, where `alter type ... add value` cannot. The three places that must agree are the constraint, `PartnerProductType` in `lib/types/database.ts`, and `PARTNER_PRODUCT_TYPES` + its label map in `lib/partner-jobs/types.ts` — everything downstream (the job form's dropdown, the zod submission schema, both job views) is data-driven off that array and needs no change.
  - `20260827000000_partner_job_item_attachments.sql` — **per-product notes and artwork** on a partner job (see **Print-partner job portals**): `design_job_items` gains `notes` + `item_number`, `design_job_files` gains a nullable `item_id`, and both RPCs are rewritten. `item_id` is **nullable on purpose and stays that way** — every file filed before this belongs to the job rather than to any one product, which is a real state rather than an unfinished backfill, and the job views render those under "Job files". Item ids are now **minted in the browser** (the mylar-design pattern) because a file is attached to a product before either row exists; `update_design_job` therefore **reconciles the item set by id instead of replacing it**, since the old delete-then-insert would cascade every per-product file away on a rename. `item_number` is stored rather than derived from `created_at` for the same reason `design_number` is on a mylar design.
  - `20260828000000_partner_job_done.sql` — **superseded by `20260829180000`; read that one first.** The partner rep's **done checkbox** as originally built: `design_jobs` gains a nullable `partner_done_at`, plus a partial index on the ticked rows. **Deliberately a new column rather than letting a rep write `status`** — `status` is the studio's field, kept that way by `protect_design_job_columns()` (`20260826000000`), and merging the two would mean the studio moving a job to `in_progress` silently un-ticks the rep's box. **No policy or trigger change was needed to make it writable**: `design_jobs_partner_update` already grants a rep UPDATE on their own jobs and the trigger forces back only the five columns it names, which is that trigger's intended design and not a gap in it. The one trigger edit is a **normalization**: any rep-side transition into the done state is re-stamped `now()`, since the column is rep-writable and a job stamped "done in 2031" is a lie the studio would read as truth. See **Print-partner job portals**.
  - `20260829000000_partner_portal_activity.sql` — **the portal's activity log, notification config, and an honest `updated_at`**, in three additive pieces that touch no existing table. (1) A trigger on `design_job_files` bumps its job's `updated_at`, because the two things that most often happen to a job — artwork added, artwork removed — are INSERTs on a CHILD table, so before this a job could gain six files and still sort as untouched; that sort is the jobs grid's default, so the trigger is what makes the default honest. Files only: item changes already go through `update_design_job()`, which updates the job row itself. (2) `partner_job_events`, scoped by `company_id` like every other partner table. `job_id` is **`on delete set null`, not cascade**, with `job_number`/`job_name` denormalized beside it — a "job deleted" event whose own foreign key deleted it would be useless, and the feed renders with no join. Reps get **SELECT and nothing else**: writes go through `log_partner_job_event()` (`SECURITY DEFINER`), which **derives** company, actor and the job's identity instead of accepting them, so a rep cannot forge an event, attribute one to another company, or amend the record of what they did. `p_actor_label` is honored only for the service role, which has no `auth.uid()` to read a name from. Its fallback to the caller's own company is reachable **only** by `job.deleted` (`20260829120000`), so every other event type must name a job that actually exists. (3) `partner_notification_settings` — RLS on with **no policies** plus an explicit revoke, the `workspace_admins` model, for the mirror-image reason: a company must not be able to change who is told about its own activity. Every column has a working default and the table may hold **zero rows**. `muted_events` is an **opt-out** list so a new event type notifies by default rather than being silently dropped by every pre-existing row.
  - `20260829120000_partner_event_delete_only_fallback.sql` — **narrows `log_partner_job_event()`'s fallback to deletions**. That function falls back to the caller's own company when the job it names cannot be found, which exists for exactly one case: a `job.deleted` event, whose job is genuinely gone by the time it is logged. The fallback was unconditional, so a rep could pass a non-existent job id with *any* event type and a made-up job number and land a fabricated row in their own company's log — which also emails the studio. Not a tenant-isolation failure (always their own company, actor still derived from `auth.uid()`, still unreadable and unamendable by them), but an audit trail is worth only as much as its resistance to being written by hand. The fallback now requires `p_event_type = 'job.deleted'`; every other type must name a job that exists. **"Not yours" and "does not exist" raise the SAME errcode and the SAME message** — distinguishing them would hand a rep an existence oracle for other companies' job ids. Do not "improve" either message.
  - `20260829180000_shared_job_complete_state.sql` — **ONE shared "complete" state, reversing `20260828000000`**. (Its restriction on WHICH statuses a rep may store was itself widened by `20260831113855`; the shared-field decision below still stands.) That migration gave the rep their own `partner_done_at`, deliberately separate from the studio's `status` so neither side could overwrite the other. The studio wanted the opposite: the admin list and the partner portal should show the SAME answer, so ticking a job complete in either place means complete in both. `status` is now the single source of truth. A rep may write it, but **only the two moves a checkbox can make** — `anything -> completed` and `completed -> in_progress`. Everything else is still silently reverted by `protect_design_job_columns()`, so `new` vs `in_progress` stays the studio's, behind the Status dropdown. Un-ticking lands on `in_progress` rather than `new` because `new` is the one answer certainly false about a job somebody has already worked on. `company_id`/`job_number`/`submitted_by`/`created_at` are immutable to reps exactly as before. **`partner_done_at` is retired, not dropped** — nothing reads or writes it (the trigger now reverts rep writes to it too), and it is kept for a release the way `0024` kept the legacy mylar artwork columns; the `drop column` and its pre-check are in the migration's trailing comment. 0 rows had it set, so there was nothing to backfill.
  - `20260831113855_partner_job_status_dropdown.sql` — **reps now set the FULL lifecycle, not just done/not-done.** `protect_design_job_columns()` is rewritten to drop `status` from the columns it forces back, so a partner may store any of the three values `design_jobs_status_check` allows (`new` / `in_progress` / `completed`) through the compact dropdown on their jobs dashboard. **Nothing else widened**: `company_id`, `job_number`, `submitted_by` and `created_at` are still reverted for any caller with an `auth.uid()`, and the retired `partner_done_at` (`20260828000000`) is now reverted too — the trigger's one addition — so a stale client cannot resurrect a second completion state. The UPDATE policy is untouched; the company boundary is still `partner_company_id()`, and the admin/service-role path is unaffected because it has no `auth.uid()`. The migration's trailing comment holds the verification updates to run as a signed-in rep.
- `lib/types/database.ts` is a **hand-maintained mirror** of that schema (the `Database` generic typing all Supabase clients). When you change the SQL, update this file too — or regenerate with `supabase gen types typescript --local > lib/types/database.ts`.
- **RLS is owner-scoped, with three deliberate exceptions.** Every table *except the seven policy-less ones* — the five anonymous-intake tables (`mylar_printing_inquiries`/`mylar_designs`/`mylar_artwork_files`, `custom_design_requests`/`custom_design_request_files`) plus the two workspace-identity tables (`workspace_admins`/`workspace_owner`) — carries an `owner_id`, scoped since `20260824193000` to **`current_owner_id()`** rather than `auth.uid()` directly (they are the same value for everyone but a workspace admin — see **Workspace admin ownership**): the anon key reads and writes nothing, users see only their own records, and portal users only their one client's rows. The intake tables have **no `owner_id` to scope to** — there is no account behind an anonymous submission — so they instead run RLS on with **no policies at all** and are reachable only through the service-role client; the two workspace-identity tables use that same model for the opposite reason, because a table that decides who is an admin must not be readable or writable by the users it judges. The **five partner tables** (`partner_companies`/`partner_users`/`design_jobs`/`design_job_items`/`design_job_files`) are the third shape: they have real policies, but scoped by `partner_company_id()` rather than by an owner, because a partner job belongs to the print company that filed it and no TD Studios admin owns it — which is why admin access to them runs through the service role. That is why the service-role surface is wider than "portal-user creation": it now also covers those intakes end-to-end (`lib/mylar-printing/queries.ts`, `lib/design-requests/queries.ts`, their actions and asset routes), the `/premadedesigns` manifest (`lib/premade-designs.ts`), the public-bucket gallery listings (`lib/data.ts`), and `/qr/history`. **Everything else — every owner-scoped read and write, and the invoice PDF route — still goes through the cookie-scoped client.** When adding to the service-role set, re-assert `requireAdmin()` at every caller and never return its results unfiltered.
