# Client portals & secure file storage

_Feature deep-dive extracted from `CLAUDE.md`. That file holds the repo-wide conventions, commands and verification gate; this one holds only the portal file/project layer._

- Admins manage portal logins and files under `/client-portals` (`app/actions/portal.ts`); portal users live under `/portal/*` (`app/actions/portal-client.ts`). Files are organized into three categories — `uploads` / `final_files` / `invoices` — mapped to storage path prefixes in `lib/portal.ts`.
- Files live in the **private `client-files` bucket**, keyed `{clientId}/{prefix}/{safeName}`. They are never served by raw object URL: downloads go through `app/api/files/[fileId]/route.ts`, which authorizes the request and returns a short-lived (60s) **signed URL**. `?inline=1` on that route mints a signed URL *without* the download disposition for inline preview, but only for `previewKind()` types (non-SVG images + PDF — `image/svg+xml` is deliberately excluded to avoid inline-SVG script execution); anything else silently degrades to a download. Portal users can upload only when the admin has enabled it (enforced in the action *and* by Storage + table RLS).
- **Projects (`0016`):** `client_projects` groups a client's files under a named unit of work with a status workflow (`draft` → `in_progress` → `awaiting_review` → `revision_requested` → `approved` → `completed` → `archived`). Portal users get **SELECT-only** access via RLS, and only to non-`draft`/non-`archived` projects; **archived files** (and files whose project is hidden) disappear from the portal too. Domain constants live in `lib/projects.ts` (`PROJECT_STATUSES`, `PROJECT_STATUS_LABEL`, `PORTAL_HIDDEN_PROJECT_STATUSES`, `isPortalVisibleProject()`) — **keep `PORTAL_HIDDEN_PROJECT_STATUSES` in sync with the RLS predicate in `0016`**, since the admin preview re-applies it in code. Portal pages: `/portal` (overview: welcome, active projects, recent files, invoice summary), `/portal/projects[/[projectId]]`, `/portal/account`. Admin: `/client-portals/[clientId]` (Projects card + `CreateProjectDialog`), `/client-portals/[clientId]/projects/[projectId]` (edit + file management), and `/client-portals/[clientId]/preview/**` (**"view as client"** — admin session, no impersonation, re-applies the portal's visibility filters in code so a draft project 404s exactly as it would for the client). Project writes are in `app/actions/projects.ts` (admin-only via `requireOwnedClient`, moved with `toFieldErrors` into `lib/action-helpers.ts` so both `"use server"` action files can share them).
- **Admin uploads are direct-to-Storage** (`app/actions/uploads.ts` + `components/portal/admin-multi-upload.tsx`): a server action validates + mints per-file **signed upload URLs** (`createSignedUploadUrl`), the browser `PUT`s bytes straight to Storage with XHR progress, then `finalizeUploadAction` verifies the object via `storage.info()` (authoritative size/MIME — never trusts the client) and writes the `client_files` row, removing the orphan if the insert fails. This bypasses the ~4.5 MB Vercel Server-Action body cap; the extension/size allowlist lives in `lib/uploads.ts` (`.png .jpg .jpeg .webp .gif .svg .pdf .ai .psd .eps .zip`, 25 MB/file, 20/batch), enforced at mint time and by the bucket `file_size_limit`. The old single-file `adminUploadFileAction` was removed; the **portal-side** single-file upload (`uploadOwnFileAction`) stays and is capped at ~4 MB by `serverActions.bodySizeLimit` in `next.config.ts`.
- **Portal file browser (DAM):** `/portal/files` is a Drive-style asset browser (`components/portal/file-browser.tsx`, domain helpers in `lib/dam.ts`): sidebar views (all/recent/favorites/categories/project folders/activity timeline), client-side search + sort, grid–list toggle, thumbnail cards (via `/api/files/[id]?thumb=1` — inline like `?inline=1` but **skips the activity log** so grids don't flood it), a preview modal with metadata + prev/next, per-user **favorites** (`client_file_favorites`, migration `0019`, optimistic star via `toggleFavoriteAction` in `app/actions/favorites.ts`), and heuristic **version grouping** (name-normalized in `lib/dam.ts` `versionKey()` — `logo-v2`/`logo (3)`/`logo_final` collapse into one card with a Version history panel; no schema). `0019` also adds the portal SELECT policy on `file_activity` powering the timeline. All data is fetched RLS-scoped in the page server component.
- **Forced password change:** provisioned logins (the admin invite and the Marty bootstrap script) set `client_users.must_change_password = true`. `getPortalContext()` surfaces it as `PortalContext.mustChangePassword`; the `(portal)` layout renders a non-dismissable banner until the user changes their password at `/portal/account` (`changePasswordAction` → `clear_must_change_password()` RPC). The `/reset-password` recovery flow clears it too (best-effort RPC).
- **Provisioning script:** `scripts/create-marty-client.ts` (run via `npm run client:create-marty`, executed with `node --env-file=.env.local` — native TS, no new deps) is an **idempotent** one-time bootstrap for a portal client. It resolves the owner from `ADMIN_EMAILS[0]` (service-role inserts get no `auth.uid()` default), find-or-creates the auth user (`email_confirm: true`, temp password from `MARTY_TEMP_PASSWORD` — never hardcoded), the `clients` row, the `client_users` mapping (`must_change_password: true`), and a starter project. Never resets an existing password unless `--reset-password`.
