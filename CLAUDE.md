## Environment variables

`.env.example` is the template. Every read/write is guarded by `isSupabaseConfigured()` / `isSupabaseAdminConfigured()` / `isResendConfigured()`, so **all of these are optional** — missing vars degrade gracefully (empty states, disabled email) rather than crashing. The individual Architecture sections below explain where each is used; this is the consolidated index.

| Variable | Used by | Notes |

## Conventions

App Router project. `app/layout.tsx` is the root layout. **Global font is Bebas Neue**: the layout loads Bebas Neue + Geist + Geist Mono via `next/font` and applies `font-sans`, but `app/globals.css` maps `--font-sans`, `--font-mono`, *and* `--font-heading` all to `--font-bebas` — so effectively everything renders in Bebas Neue (single 400 weight, no lowercase). Geist stays loaded only as a fallback variable.

- **Import alias:** `@/*` maps to the repo root (e.g. `@/lib/utils`, `@/components/ui/button`).
- **Styling:** Tailwind CSS **v4** — there is no `tailwind.config.*`. Configuration and theme tokens live in `app/globals.css` via CSS (`@theme`/CSS variables); PostCSS is wired in `postcss.config.mjs` with `@tailwindcss/postcss`.
- **UI components:** shadcn/ui (`components.json`), style `radix-lyra`, base color `neutral`, RSC enabled. Generated primitives live in `components/ui/`. Add components with the `shadcn` CLI rather than hand-writing primitives. Non-shadcn UI dependencies, all deliberately scoped: `GlassCard` from `@developer-hub/liquid-glass` powers the glassy card on the public home card and login panel (`app/home-card.tsx`, `app/login/login-panel.tsx`); **`react-social-icons`** is used in exactly one place, `app/home-card.tsx`, for the Instagram badge only (it ships no Cash App / SMS / Chime mark, so those three are hand-built to match its 40px circle); **`react-konva`/`konva`** and **`@dnd-kit/*`** exist only for the mockup tools (`app/tools/8pc-mockup-generator/`, `app/tools/bag-mockup-grid/`) — don't reach for either elsewhere.
- **Icons — two libraries, split by area; match the file you're editing.** **Phosphor** (`@phosphor-icons/react`) is the choice for **new code**: every public/standalone page uses it (`portfolio`, `taste-budz`, `gso`, `designs`, `mafiaterpz`, `martyig`, `tools/*`, `qr-generator`, `custom-design-request`, `sign-up`, `home-card`, `login`), as does the newest admin work (`components/dashboard/task-manager.tsx`, `components/portal/file-browser.tsx`, `app/(app)/qr/page.tsx`, `(customer)/account`) and four hand-swapped shadcn primitives (`dialog`, `dropdown-menu`, `select`, `sheet`). **`lucide-react` is still the icon set across the older admin `(app)` pages and most of `components/portal/`** — including `components/layout/nav-config.ts`, `app-shell.tsx`, and `components/dashboard/stat-card.tsx` — plus the remaining shadcn primitives. Don't mix both in one file: when editing existing code, use whichever that file already imports.
- **`cn()` helper:** `lib/utils.ts` merges classes with `clsx` + `tailwind-merge`; use it for conditional classNames.
- **Public pages share a CSS layer, not a utility string — use it on any new standalone route.** Four classes in `app/globals.css` replace what used to be copy-pasted into a dozen `<main>` tags, and each encodes a decision worth not re-litigating: **`.public-page`** is the shell padding (`max()`-based `env(safe-area-inset-*)` so landscape content clears the notch rail and the last control clears iOS Safari's floating toolbar; a smaller top pad on phones, resolving to the desktop 24/48px frame from `sm` up) — **do not go back to a bare `px-4 py-12`**; **`.public-title`** is the h1 scale (a `clamp()` rather than a breakpoint pair, because the interesting range is 320→430px and lives *inside* Tailwind's first breakpoint); **`.on-glass`** lifts muted text inside a tinted panel; and **`.text-on-photo`** is for text with no panel between it and the backdrop — it pairs a lifted tone with a two-layer per-glyph `text-shadow`, the one case here where a text-shadow is the right tool, since centred headers land on the brightest part of the image where even pure white is ~1.1:1. All four are **scoped to public routes**; the admin/portal shells keep their zinc palette untouched.
- **Two shared marks on public pages:** `HomeLogoLink` (`components/layout/home-logo.tsx`) at the top and `BackToStudiosLink` (`components/layout/public-page-link.tsx`) at the bottom — the latter is on ~17 public routes, so add it to a new one rather than hand-rolling a back link.
- **`next.config.ts` is a required stop for four kinds of change** (each detailed in its own section below): adding a **cutline preset** or any other asset read with `fs` at runtime (`outputFileTracingIncludes` — unlisted assets are missing from the Vercel function); serving a new **static HTML site** from `public/` (`rewrites()` — the public folder doesn't resolve `index.html`); changing **portal upload / body-size** behavior (`experimental.serverActions.bodySizeLimit`, currently `4mb`); and enabling **remote images** (`images.remotePatterns` currently permits only short-lived signed Storage images for `/premadedesigns`).
- **Forms, validation, toasts, dates:** Forms are Server-Action driven (`useActionState` against `ActionState`, ~20 call sites) — **not** react-hook-form. Input validation is **`zod`**, applied *server-side* inside the Server Actions (`app/actions/*` all import it); there is no client-side schema layer. `react-hook-form` + `@hookform/resolvers` are in `package.json` but currently unused in app code — don't reach for them. User feedback is **`sonner`** toasts (`components/ui/sonner.tsx`). Date/currency formatting goes through `lib/format.ts` (backed by **`date-fns`**) — see Data flow.

## Architecture

A Supabase-backed invoicing app: clients, auto-numbered invoices with line items / tax / discounts, payments, and a dashboard. `README.md` covers the same ground at a shallower depth — features, the route tables, setup, and the deploy checklist — and is currently accurate; **update it alongside this file** when you add a route, a migration, an env var, or a bucket. It is the orientation doc, this is the architecture doc: where the two disagree, this file wins. The points below are the non-obvious wiring.

### Routes & rendering

- Admin app lives under the `app/(app)/` route group, wrapped by `AppShell` (sidebar + mobile sheet nav). Client-portal pages live under the separate `app/(portal)/` group (`/portal/*`), wrapped by its own shell. Self-signup customers live under a third group, `app/(customer)/` (`/onboarding`, `/account`), gated by `requireCustomer()` in its `layout.tsx` (see **Auth & roles**). `app/page.tsx` (outside all groups) is the public sign-in screen, reused by `/login`. The sign-in card is a "link in bio" `HomeCard` (`app/home-card.tsx`) that flips in place between three modes (`bio` / `signin` / `forgot`) rather than navigating. **It is shaped like a raffle ticket**, and that shape is load-bearing for how you edit it:
  - **`BIO_LINKS` is the whole link surface, and `tier` is the layout.** One entry is `tier: "prize"` (the full-width gold row, which also takes a `sub` second line) and the rest are `tier: "tile"` (the two-column grid beneath, in array order). **Exactly one `prize` is expected** — a second spends the accent twice and flattens the hierarchy. `sameTab` is set on in-app routes *and* on the `sms:` handoff, since an OS-handled navigation opened with `target="_blank"` strands an empty tab behind it. `sticky` marks the single link the phone-only floating CTA mirrors once it scrolls out of view — a flag rather than a second hardcoded href, so the two can't drift.
  - **There is no `SOCIAL_LINKS` array.** The four brand marks (Instagram, Cash App, `sms:`, Chime-handle copy-to-clipboard) are hardcoded in the `SocialRow` component, which renders **inside the ticket stub** under the positioning line — not in the footer, which keeps the small print alone.
  - **Ticket visuals (`.tk-*`) live in `app/globals.css`; the mobile entrance animation lives in a `<style>` block inside `app/home-card.tsx`.** That block is plain CSS on purpose — the landing page shouldn't wait on framer-motion to hydrate. **Do not animate `opacity` on `.home-enter-card`**: a filling opacity animation promotes it to a Chromium Backdrop Root permanently, which silently kills the card's `backdrop-filter` frost (it computes fine in devtools and never composites). Children fade individually instead. `prefers-reduced-motion` drops travel/sweep/parallax entirely.
  - **Responsive sizing is a viewport-height custom-property scale**, not per-element breakpoints: `.home-shell` declares `--home-pad` / `--home-logo` / `--home-link-h` / `--home-cta-room` etc. in `app/globals.css`, re-declared at short-screen heights. Retune the scale rather than adding one-off classes. Scroll-linked parallax comes from `useScrollParallax` (`app/use-home-scroll.ts`).

  The other public/standalone pages share one brand mark, `HomeLogoLink` (`components/layout/home-logo.tsx`) — the circular logo linking to `/` (the proxy then routes authed visitors to their role home); the admin/portal shells use their own `Brand`/`PortalBrand` instead. The homepage backdrop is **viewport-split**: `HomeMobileBackground` (`app/home-mobile-background.tsx`, a `fixed` `object-contain` `next/image` of `public/home-mobile-bg.jpg`) below `md`, `AnimatedBackground` from `md` up — the two are mutually exclusive, so change both if you change one.
- **Public (no-auth) pages outside both groups** (all allow-listed in `proxy.ts`): `app/qr-generator/page.tsx` (a public QR generator, the same `QrGenerator` component with `allowSave={false}` — its home-card button was removed, so it's reached by URL only); `app/premadedesigns/page.tsx` (the "premade designs" gallery at **`/premadedesigns`** — it used to live at `/qr-generator/designs`, which now `redirects()` here in `next.config.ts`; it is unrelated to the QR generator. No DB, but **bucket-backed**: `force-dynamic`, reading the public `DESIGNS` bucket via `getDesignsImages()` so uploads appear with no redeploy. It formerly read `public/promoimages` with `fs.readdir` at build time; that folder and its `outputFileTracingIncludes` entry are gone. It is the **only** gallery that renders bucket images through `next/image`, which is why the Supabase Storage host is allow-listed in `images.remotePatterns` — the others use plain `<img>`. It is also the only one sorted **newest-first**, which relies on the filenames being Instagram exports with a 9-digit leading media ID); `app/custom-design-request/page.tsx` (a public, no-auth custom-design request form reached from the home "link in bio" card. **It used to post to Formspree; it now persists** to `custom_design_requests` + `custom_design_request_files` (migration `20260822182058`) and is worked from `/design-requests` in the admin group — see **Custom design requests**. Reference files still upload browser→Storage into the private `design-requests` bucket (migration `0021`) via the anonymous-safe service-role actions in `app/actions/design-requests.ts`); `app/q/[slug]/page.tsx` (the dynamic-QR redirect — see the QR section); `app/portfolio/page.tsx` (the public Portfolio Gallery — see Portfolio Gallery); `app/whiteash/page.tsx` (the **White Ash Farms client proof gallery** — public but `noindex`, shared by link; see Portfolio Gallery); `app/tools/cutline-generator/page.tsx` (the public, no-auth Cutline Generator — see Cutline Generator); `/mylar` (the **static Mylar shop** — a fully self-contained single-file HTML site at `public/mylar/index.html`, not a React route: it's served via a `rewrites()` entry in `next.config.ts` mapping `/mylar` → `/mylar/index.html`, since the public folder doesn't resolve `index.html` automatically; all CSS/JS/images are inline, its cart/forms are client-side only with no backend; the home-card "Enter Here" button to it was removed while the shop is in progress, so it's currently reached by URL only); `app/tools/mockup-generator/page.tsx`, `app/tools/8pc-mockup-generator/page.tsx`, and `app/tools/bag-mockup-grid/page.tsx` (the three public, no-auth **mockup tools** — see Mockup tools); `app/mylar-printing/page.tsx` (the public, no-auth **Custom Mylar Printing wizard** — the home card's primary CTA; one of the two public forms here that *persist*, alongside `/custom-design-request`; see Custom Mylar Printing); `app/mylar-bag-printing/page.tsx` (an earlier, simpler **mylar bag order form** — the Formspree + `design-requests`-bucket pattern `/custom-design-request` used to share, no DB and no order records; bag styles and the quantity/pricing rules live in `app/mylar-bag-printing/bag-types.ts`. - **Current `/premadedesigns` implementation (supersedes the legacy `DESIGNS` wording above):** the public route is server-gated by the `0420` keypad and a signed httpOnly cookie. **It is reached by URL only** — the home card's "Premade Designs" tile deliberately points at the Instagram grid instead, so don't "fix" that href to `/premadedesigns`. Only unlocked sessions receive the private `premade-designs` bucket manifest and one-hour signed URLs for whatever is currently on screen. The complete 2,312-image manifest comes from the service-role-only `list_premade_design_paths()` RPC, is cached for 60 seconds, and powers the whole gallery client-side. **It is a two-view gallery, not a flat grid:** the index shows one box per bucket folder (94 of them) with a cover image and a design count, and clicking one opens that collection's designs. `buildPremadeCollections()` in `lib/premade-designs-types.ts` is pure and shared — the page calls it to know which covers to sign, the client calls it to render — so both always agree on a folder's cover. **Only the visible view is ever signed**: 24 covers on the index (`PREMADE_COLLECTIONS_PAGE_SIZE`), 36 designs inside a collection (`PREMADE_DESIGNS_PAGE_SIZE`), and `getPremadeDesignUrlsAction` caps one request at the larger of the two. Search is contextual — collection names on the index, design names inside a collection — and a bucket with one folder (or none) skips the index entirely. **Every bucket image carries the TD Studios watermark** (`DesignWatermark` in `gallery.tsx`) at 85% opacity — design cards, collection covers, and the lightbox alike. It is `pointer-events-none`, so it never steals the card's click or the lightbox's close-on-backdrop, and it sits *under* the right-click deterrent span rather than replacing it. Its asset (`public/premade-watermark.png`) is pre-resized to 800px wide on purpose: like everything else in this gallery it renders `unoptimized`, so whatever is committed is what ships to every card. Its `next/image` instances deliberately set `unoptimized`, so browsers fetch the signed Supabase URLs directly; the production Vercel Image Optimization endpoint currently returns `OPTIMIZED_IMAGE_REQUEST_PAYMENT_REQUIRED` and must not sit in this gallery's delivery path.
- All four data-backed groups (`(app)`, `(portal)`, `(customer)`, `(partner)`) set `export const dynamic = "force-dynamic"` in their `layout.tsx` because every page reads from Supabase per request. Keep new data-backed pages inside the appropriate group.
- `proxy.ts` (Next.js 16's renamed Middleware, Node.js runtime) runs on every request: it refreshes the Supabase session (rotating cookies), maps **print-partner hostnames and path aliases** onto the internal `/partner/<slug>/…` routes (see **Print-partner job portals**), and optimistically redirects unauthenticated users to `/login` and authenticated users away from it. **It no longer writes cookies straight onto a `NextResponse.next()`**: which response it returns (next / rewrite / redirect) isn't known until after the session is read, so rotated cookies are collected and applied to whichever one it ends up building — a refreshed session must survive all three. `PUBLIC_PATHS` = `/`, `/login`, `/sign-up`, `/reset-password`, `/qr-generator`, `/premadedesigns`, `/custom-design-request`, `/how-to-order`, `/mylar-bag-printing`, `/mylar-printing`, `/auth/callback` (the OAuth code exchange must be reachable before cookies exist), `/portfolio`, `/taste-budz`, `/gso`, `/designs`, `/martyig`, `/mafiaterpz`, `/tools/cutline-generator`, `/tools/mockup-generator`, `/tools/8pc-mockup-generator`, `/tools/bag-mockup-grid`, `/mylar` (+ `/mylar/index.html` — the matcher only skips image extensions, so the direct `.html` path needs allow-listing too), plus prefix matches for any `/q/<slug>` redirect. The proxy is **not** the real gate — enforcement is Postgres RLS plus `requireUser()`/`requireAdmin()`/`requirePortalUser()` in Server Components and Actions.

### Data flow

- **Reads:** `lib/data.ts` holds core query helpers (`getInvoices`, `getInvoice`, `getDashboardStats`, the QR helpers `getQrCodes`/`getQrCodeById`/`getQrScanCounts`/`getQrScansForQrCode`/`getQrScanSummary`, etc.), called directly from Server Components. Display formatting (currency, dates) goes through the shared helpers in `lib/format.ts` — use them rather than ad-hoc `Intl`/`toLocaleString` calls so amounts and dates render consistently across pages.
- **Writes:** Server Actions in `app/actions/` (`"use server"`): `clients`, `invoices`, `settings`, `qr`, `tasks` (the dashboard task manager), and `profile` for the admin/customer app; `auth` (sign in/out, password reset), `portal` (admin-side portal-user + file management), `portal-client` (client-side portal uploads), `projects` (admin-only client-project CRUD — see Client portals), `uploads` (mints signed upload URLs + finalizes admin direct-to-Storage uploads), `favorites` (per-user portal file stars), `design-requests` (the public custom-design form's anonymous-safe service-role uploads **and** its validated submission), `custom-design-requests` (the admin-only status write for those — split out from the public file for the same reason as `mylar-requests` below), `mylar-printing` (the public quote wizard's anonymous submission + artwork upload path), `mylar-requests` (the admin-only status write for those inquiries — kept in a separate file so the public wizard's bundle never references an admin endpoint), `partner-auth` + `partner-jobs` (the print-partner portal's sign-in, upload tickets and job submission), and `admin-partner-jobs` (the admin-only status write for those — same split, same reason). **Every partner-side write ends with one `recordPartnerJobEvent()` call** (`lib/partner-jobs/events.ts`), which logs a `partner_job_events` row and hands the announcement to `lib/notifications/dispatch.ts` — the only notification seam in the codebase. See **Print-partner job portals**. They validate inputs, authenticate inside each action, then `revalidatePath(...)` the affected routes. Forms are client components using `useActionState` against the shared `ActionState` shape in `app/actions/types.ts` (`{ error?, fieldErrors?, success? }`) or progressive-enhancement forms with `useFormStatus`.
- **Graceful degradation:** every read/write first checks `isSupabaseConfigured()` and returns a safe fallback (empty array / `null` / a "not configured" error) when env vars are absent. This is deliberate — the app builds and the UI renders empty states with no database. Preserve this guard in new data code.

### Three Supabase clients (do not mix them)

1. **SSR client** — `lib/supabase/server.ts` (`createClient()`) and `client.ts`, via `@supabase/ssr`. Used by Server Components and Server Actions; RLS-scoped through the anon key + auth cookies. Env: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
2. **Route-handler client** — `lib/supabase/with-supabase.ts` (`supabaseRoute(config, handler)`), via `@supabase/server`. Used only by API routes under `app/api/` (e.g. `app/api/clients/route.ts`). `ctx.supabase` is RLS-scoped; `ctx.supabaseAdmin` bypasses RLS. `auth: "secret"` requires the secret key in the `apikey` header; `auth: "none"` is for public endpoints (e.g. `app/api/health/route.ts`, an unauthenticated health check). Env: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`, `SUPABASE_JWKS_URL`.
3. **Service-role admin client** — `lib/supabase/admin.ts` (`createAdminClient()`, guarded by `isSupabaseAdminConfigured()`), via `@supabase/supabase-js`. **Bypasses RLS.** Use only on the server and only for operations the cookie-scoped client can't do: creating client-portal auth users via `auth.admin.createUser` (inside `requireAdmin()`-guarded Server Actions), and **listing the public `custom-work` bucket** for the Portfolio Gallery (`getPortfolioImages`), where the only data returned is public filenames + URLs from an already-public bucket. Never import it into a Client Component or return its results unfiltered. Env: `SUPABASE_URL`, `SUPABASE_SECRET_KEY`.

### Auth & roles

- **Auth is live** (Supabase Auth: email/password plus **Google OAuth**). Google sign-in starts from `app/login/google-sign-in-button.tsx` (`signInWithOAuth`, PKCE); Supabase redirects back to `app/auth/callback/route.ts`, which exchanges the code for a session (setting cookies via the SSR client) and lands the user on `roleHome()` — same role routing as `signInAction`. The `redirect` param carries the original destination through the round-trip; only same-origin in-app paths are honored. As a safety net, `app/page.tsx` forwards a stray `?code=` (when Supabase's Redirect URLs allowlist is missing `/auth/callback` and OAuth falls back to the Site URL) on to `/auth/callback` so the exchange still happens. Helpers in `lib/auth.ts`: `getUser()`/`requireUser()` (any session), `requireAdmin()`, `getPortalContext()`/`requirePortalUser()`, and `requireCustomer()`. Admins are created in the Supabase dashboard; portal users via the admin action; **customers self-sign-up at `/sign-up`**.
- **Four roles, with admin determined by an explicit allowlist — never inferred from missing data.** `roleHome()` encodes the precedence, and the order is load-bearing (admin → portal → partner → customer):
  1. **admin** — email is in the server-only `ADMIN_EMAILS` env allowlist (`isAdminEmail()`). Full `app/(app)` dashboard. **`ADMIN_EMAILS` must be set or no one can reach the dashboard.**
  2. **portal user** — has an active (`revoked_at is null`) `client_users` row. Confined to `/portal/*`, mapped to one client.
  3. **print-partner rep** — has an active `partner_users` row whose company is also active. Confined to that company's portal (see **Print-partner job portals**). Checked *after* the portal role so a user holding both keeps the access they had before partners existed, and *before* the customer fallback so a rep with no `profiles` row is never mistaken for an un-onboarded signup.
  4. **customer** — any other authenticated user (self-signup). **A customer is a portal APPLICANT, not a separate destination**: they live in the `(customer)` group at `/account/pending`, a dead-end "waiting for approval" screen, and the only thing between them and `/portal` is the `client_users` row an admin creates by approving them (see **Self-signup → portal approval**). `/onboarding` is now only the email-confirmation fallback, and `/account` is a bare redirect to `/account/pending`.
- **Security:** admin status lives *only* in config a user cannot write — the `ADMIN_EMAILS` env allowlist that gates routes, and its database counterpart `workspace_admins`, which is RLS-on-with-no-policies and reachable only by the service role (see **Workspace admin ownership**). Neither is user-writable, so a customer can never self-promote (the `profiles` table deliberately has no role column). `roleHome()` computes the right landing path and `signInAction` routes each role there. Admins read/manage `profiles` via the service-role client (`lib/supabase/admin.ts`), since profile RLS is owner-only. Migration: `0009_profiles.sql`.

### Workspace admin ownership — several admin logins, ONE dataset

`ADMIN_EMAILS` gates **routes**; Postgres cannot read it. So before migration `20260824193000`, every owner-scoped policy said `owner_id = auth.uid()` and a *second* admin passed `requireAdmin()`, reached `/dashboard`, and saw an empty app — worse, `0003`'s write policies rejected inserts into the shared dataset, so they could only fork a private one (burning numbers from the global `invoice_number_seq` on the way).

- **The fix remaps the identity; it never widens the predicate.** `public.current_owner_id()` (`SECURITY DEFINER`, fixed `search_path`, same shape as `portal_client_id()`) answers "which `owner_id` may I act as?" — the canonical workspace owner for a workspace admin, plain `auth.uid()` for everyone else. Policies became `owner_id = (select public.current_owner_id())`, wrapped in a `select` so Postgres hoists it into a once-per-statement InitPlan. Predicate *shape* is unchanged, so `with check` still blocks ownership reassignment and `0017`'s `exists (… clients c …)` hardening survives verbatim on every policy it added it to. **Never drop that sub-clause when editing these policies** — it is the whole of the `0017` fix.
- **Two tables, both unreachable by users.** `workspace_admins` (uid allowlist, mirroring `ADMIN_EMAILS`) and the singleton `workspace_owner` (the one uid every owner-scoped row is written under) run RLS with **no policies** and `revoke all … from anon, authenticated` — the anonymous-intake model from `20260822182058`. Only the service role and the `SECURITY DEFINER` helper read them, which is what keeps "admin" out of user-writable rows.
- **Portal users and workspace admins are mutually exclusive, enforced by a trigger pair** (`assert_not_portal_user` / `assert_not_workspace_admin`, both raising `42501`) rather than in application code, since a `check` constraint cannot see another table. Setting `revoked_at` still passes, so nothing blocks restoring a portal mapping.
- **`ownerId` and `userId` are different ids and are not interchangeable.** `currentOwnerId()` in `lib/auth.ts` calls the *same* RPC the policies use rather than recomputing the answer — a mismatch would fail `with check` and reject the write. Every `owner_id` column takes `ownerId`; **attribution columns (`actor_id`, `uploaded_by`) take `userId`**, so the activity timeline still shows which admin acted. `requireOwnedClient()` (`lib/action-helpers.ts`) returns both. A null from the RPC is an **error to surface** (`OWNER_RESOLVE_ERROR`), never a fall back to `user.id` — that fallback is exactly the forked-dataset bug this exists to prevent. Threaded through `clients`, `invoices`, `portal`, `projects`, `qr`, `settings`, `tasks`, `uploads`.
- **Deliberately not remapped:** `profiles` (owner-only; admins read it via the service role), `client_file_favorites.using` (a star is personal — only its client-ownership sub-clause moved), `file_activity.actor_id`, `qr_generations` (no policies), and `cutline_files_owner_all`. Existing rows were **not** re-owned — all 13 owner-scoped tables already belonged to one uid.
- **Storage is part of the fix, not an afterthought:** the `client-files` admin policy on `storage.objects` is remapped too, or other admins reach the file *rows* but not the *bytes*. Portal storage policies (`0004` insert, `0018` select) are untouched.
- **`npm run admin:sync` does not exist yet.** The migration's comments and `OWNER_RESOLVE_ERROR` both point at it as the authoritative, idempotent seeder for `workspace_owner` / `workspace_admins`; today the only seed is the migration's own best-effort `insert … where lower(u.email) = 'tyler.diorio@gmail.com'`. Until that script lands, **add each new admin's uid to `workspace_admins` by hand** (service role) alongside adding their email to `ADMIN_EMAILS` — the two allowlists are separate and must be kept in step. If `workspace_owner` is empty the helper fails safe to `auth.uid()`, i.e. exactly the old behavior.
- **Known pre-existing bug, called out in the migration and deliberately left alone:** the single `company_settings` row has `owner_id is null`, so no admin can see it — the settings page reads empty and `updateSettingsAction` inserts a *second* row instead of updating it. The one-line adoption `update` is in the migration's trailing comment; it predates this work and is orthogonal to it.
- **Verify as each admin with their own session, never as the service role** (which bypasses RLS and proves nothing). The migration's trailing comment holds the five checks: identity resolution, matching workspace counts, portal-user isolation, self-promotion refusal, and both directions of mutual exclusion.

### Self-signup → portal approval

How a stranger becomes a portal user. **No migration was needed for any of this** — the state is derived from tables that already existed.

- **Signup is one step.** `/sign-up` collects email, password, name, business name and — when Supabase issues a session immediately (email confirmation OFF) — `signUpAction` writes the `profiles` row itself and lands them on `/account/pending`. `phone`/`instagram` are still columns on `profiles` and still hold whatever pre-existing rows had, but are **no longer asked for**; every profile write is a partial upsert, so old values survive. With email confirmation ON there is no session to write a profile under, so the two names ride in the auth user's **metadata** and `/onboarding` prefills itself from them — a confirm-and-continue, not a second form. **`emailRedirectTo` points at `/auth/callback?redirect=/account/pending`, never at the destination directly**: Supabase appends `?code=` to that URL and only the callback exchanges it, so aiming the link at `/account/pending` (which is not in the proxy's `PUBLIC_PATHS`) meant the proxy saw no cookies, bounced to `/login`, and dropped the code on the way — a confirmed account that lands on a sign-in form. Reuse the existing callback for any future confirmation/recovery link rather than adding a second exchange point. (Metadata is self-asserted and grants nothing; it is only ever read back as a form default.)
- **"Pending" is derived, never stored.** A completed `profiles` row with no `client_users` row IS the pending state. Approval creates that row, which is what removes them from the queue — so there is no status column, no second source of truth, and nothing to keep in sync.
- **Two unique constraints, and they mean opposite things.** `client_users.user_id` is `UNIQUE` (0003) — one portal per person — and that is the idempotency guarantee: `approvePortalAccessAction` (`app/actions/portal.ts`) checks for an existing mapping first *and* catches `23505`, so a double-click, a concurrent approval, and a retry all converge on one client and one mapping. `client_users (client_id) where revoked_at is null` is UNIQUE too (`20260824022608`) — one active login per client — and losing *that* one is not idempotent at all: it means a different signup took the portal, so it reports an error. The two are distinguished by constraint name, never by the shared `23505` code. A **revoked** mapping is deliberately not resurrected here — re-granting is an explicit act on that client's portal page. A lost race that had already inserted a `clients` row deletes it again, so repeated approval never leaves empty duplicate clients behind.
- **Approval reuses an existing client, and refuses to guess.** It matches `clients.email` to the signup email through `normalizeEmail()` (`lib/portal.ts` — trim + lowercase only; it deliberately does *not* strip dots or `+tags`, since merging two real people would hand one customer another's files). Zero matches creates the client; exactly one links to it, so prior invoices/files/projects appear instantly; **two or more refuses with the names listed**, as does a matched client that already has an active portal login. Approval grants **access only**: new mappings get `can_upload: false` (the same default as the admin invite flow — uploads are enabled per client from that client's portal page when actually wanted) and `must_change_password: false`, since unlike the invite flow these users chose their own password at signup.
- **Trust boundary:** `requireAdmin()` runs before anything is read. The service-role client is used *only* to read the applicant's own `profiles` row (profile RLS is owner-only, so no admin policy exists to read it with) and to check mappings; **every write goes through the cookie-scoped client** and stays under the owner-scoped RLS from `0002`/`0017`. No policy was added, widened, or weakened.
- **Admin UI:** the `PendingPortalAccess` card at the top of `/dashboard` (`components/dashboard/pending-portal-access.tsx`, lucide icons, one `<form>` per row so approvals don't block each other). It renders nothing when the queue is empty. `getPendingPortalSignups()` in `lib/data.ts` re-asserts `requireAdmin()` itself and returns only the four display fields plus a single unambiguous client match.

### Invoice totals & status — computed in two agreeing places

- Totals (`subtotal`, `discount_amount`, `tax_amount`, `total`) are derived **both** in the browser via `calculateTotals()` in `lib/invoice.ts` (live preview while editing) **and** authoritatively in Postgres via triggers on save (`supabase/migrations/0001_initial_schema.sql`). Changing the formula means changing both. Server Actions never write totals directly — they write rates/items and let the triggers recompute.
- An invoice's stored `status` is not the whole story: `effectiveStatus()` in `lib/invoice.ts` treats a `sent` invoice past its `due_date` as `overdue` at read time. Use it for display rather than `invoice.status` directly.
- Invoice numbers (`TD-INV-0001`…) come from a Postgres sequence/trigger; never set `invoice_number` from app code.

- **RLS is owner-scoped, with three deliberate exceptions.** Every table *except the seven policy-less ones* — the five anonymous-intake tables (`mylar_printing_inquiries`/`mylar_designs`/`mylar_artwork_files`, `custom_design_requests`/`custom_design_request_files`) plus the two workspace-identity tables (`workspace_admins`/`workspace_owner`) — carries an `owner_id`, scoped since `20260824193000` to **`current_owner_id()`** rather than `auth.uid()` directly (they are the same value for everyone but a workspace admin — see **Workspace admin ownership**): the anon key reads and writes nothing, users see only their own records, and portal users only their one client's rows. The intake tables have **no `owner_id` to scope to** — there is no account behind an anonymous submission — so they instead run RLS on with **no policies at all** and are reachable only through the service-role client; the two workspace-identity tables use that same model for the opposite reason, because a table that decides who is an admin must not be readable or writable by the users it judges. The **five partner tables** (`partner_companies`/`partner_users`/`design_jobs`/`design_job_items`/`design_job_files`) are the third shape: they have real policies, but scoped by `partner_company_id()` rather than by an owner, because a partner job belongs to the print company that filed it and no TD Studios admin owns it — which is why admin access to them runs through the service role. That is why the service-role surface is wider than "portal-user creation": it now also covers those intakes end-to-end (`lib/mylar-printing/queries.ts`, `lib/design-requests/queries.ts`, their actions and asset routes), the `/premadedesigns` manifest (`lib/premade-designs.ts`), the public-bucket gallery listings (`lib/data.ts`), and `/qr/history`. **Everything else — every owner-scoped read and write, and the invoice PDF route — still goes through the cookie-scoped client.** When adding to the service-role set, re-assert `requireAdmin()` at every caller and never return its results unfiltered.

### QR code platform (dynamic links, styling, scan analytics)

- **Admin UI:** `/qr` (`app/(app)/qr/page.tsx`) lists saved codes and hosts the generator; `/qr/[id]` (`app/(app)/qr/[id]/page.tsx`) is the per-code detail/editor with its scan analytics. The reusable `QrGenerator` (`components/qr/`) is also embedded on the **public** `/qr-generator` page with `allowSave={false}`.
- **Static vs dynamic:** a static code encodes the destination directly. A *dynamic* code (saved via `saveQrCodeAction` in `app/actions/qr.ts`) gets an owner-scoped `qr_codes` row with a unique `slug`, and the printed QR encodes the stable short link `/q/<slug>` — so the destination can be repointed (`updateQrCodeAction`) or disabled (`toggleQrCodeAction`) without reprinting. Slugs are globally unique; because RLS hides other owners' rows, inserts can't pre-check and instead retry with a random suffix on a `23505` unique violation.
- **Public redirect + analytics, no table grants:** `app/q/[slug]/page.tsx` (`force-dynamic`, allow-listed in `proxy.ts`) resolves the slug through the `SECURITY DEFINER` `resolve_qr_target()` RPC (returns only `qr_code_id` + `destination_url`, never owner data), best-effort-logs a scan via `log_qr_scan()`, then 302s. Anonymous callers get **execute** on those two functions only — they never read or write `qr_codes`/`qr_scans` directly. Scan logging is privacy-preserving: a **salted, truncated SHA-256 of the IP** (`QR_SCAN_SALT` env, optional), a coarse device class, and `x-vercel-ip-country` — never the raw IP. Logging failures never block the redirect.
- **Styling is client-side and serializable:** `lib/qr/style.ts` defines the small `QrStyle` (`fg`/`bg`/`ecc`/optional base64 `logo`), persisted per code in `qr_codes.style_json`; `parseQrStyle()` coerces stored/submitted JSON back to a valid style and drops oversized/invalid logos (`MAX_LOGO_DATA_URL_LENGTH`). There is **no separate logo asset storage** — the logo is a size-capped data URL inline in the row, matching the project's "no new infra" approach.
- **Rendering runs in the browser:** `lib/qr/render.ts` (`renderQrPng`/`renderQrSvg`, logo overlay via canvas/`<image>`) and `lib/qr/pdf.ts` (single-page pdf-lib export) are pure functions called only from client components (`qr-export-buttons`, `qr-download-buttons`, `qr-preview`). Unlike the invoice PDF, QR PDFs are generated client-side.
- **Generation history (`0010`):** every code produced in the generator (admin *and* anonymous public) is logged to `qr_generations`. `QrGenerator` fire-and-forgets `logQrGenerationAction` on each new distinct encoded value (deduped per content), tagging `source` (`admin`/`public`); the action routes through the anon-safe `log_qr_generation` RPC and stores only a compact style summary (no logo data URL). Admins view it at `/qr/history` via the service-role client. Distinct from `qr_codes`, which holds only *saved dynamic* codes.

### Cutline Generator (public print-prep tool)

- **Public UI (no auth):** `/tools/cutline-generator` (`app/tools/cutline-generator/`, outside all route groups, allow-listed in `proxy.ts`) — anyone with the link can drag-drop one or many 1200×1500 JPG/PNG designs and get one **print-ready PDF per image** with a vector cut-contour overlaid; batch with **Download All ZIP**. Styled like the other public tools (`AnimatedBackground` + `HomeLogoLink`). The client component drives a per-file **uploading → processing → complete / failed** state machine (one route call per file, real upload progress via `XMLHttpRequest`, concurrency 3).
- **No persistence — direct request → response.** `app/api/cutline/generate/route.ts` (`runtime = "nodejs"`, **no auth, no Supabase**) takes ONE multipart image, composes the PDF in memory, and streams it straight back as the `application/pdf` body. Nothing is uploaded or stored; the browser holds each PDF as a blob. There is **no `cutline-files` Storage usage** in this flow (the `0015` bucket is now unused — see migrations) and there are no `zip`/`job` routes.
- **What it does (ported 1:1 from the user's Python `cutline-bulk-engine`):** the output page size **is** the cutline PDF's first-page MediaBox (default `cut-line-file.pdf` = 288×360pt / 4×5″); the artwork is drawn to fill it (1200×1500px → 300 DPI, `cover` fit, ratio preserved); the cutline page is composited **on top**. `lib/cutline/compose.ts` (`server-only`) does this with **`sharp`** (EXIF auto-orient + sRGB normalize, rescuing CMYK/16-bit/grayscale inputs raw pdf-lib rejects) then **`pdf-lib`** `embedPdf`/`drawPage`.
- **Vector cut path is preserved, never rasterized.** The contour uses a `/Separation /CutContour` spot color (Roland VersaWorks standard). Embedding the cutline as a Form XObject copies its content stream + spot colorspace verbatim — **do not** redraw the contour as a process-color rectangle. Verify post-build by checking the output PDF still carries a `/Separation /CutContour` colorspace.
- **PDF generation is server-side; only ZIP bundling is client-side.** "Download All ZIP" zips the already-generated PDF blobs in the browser with **`jszip`** — no re-upload, no storage, and it sidesteps the Vercel request-body cap that a server-side zip of many multi-MB PDFs would hit. The vector compositing never runs in the browser.
- **Safety limits** (`lib/cutline/limits.ts`, shared client+server): JPG/PNG only (MIME or extension), ≤ 30 MB per image, ≤ 25 images per batch; anything else is rejected on both sides.
- **Reusable presets:** `lib/cutline/presets.ts` (server+client-safe metadata) is the swap point — add a preset `{ id, label, file }` and drop its PDF under `public/assets/cutlines/` (`CUTLINE_ASSET_DIR`). The asset is read with `fs` at runtime, so each preset file must be listed in `outputFileTracingIncludes` in `next.config.ts` (mirroring the invoice-logo entry) to be bundled into the function on Vercel.

### Mockup tools (three public, no-auth print tools)

All three live under `/tools/*`, are allow-listed in `proxy.ts`, share the `AnimatedBackground` + `HomeLogoLink` chrome, and **cross-link to each other** from the footer of `/tools/mockup-generator`. None of them touch Supabase, auth, or any table — but they split into two very different rendering architectures, so pick the right one when extending:

- **`/tools/mockup-generator` — single bag, 100% client-side.** Artwork is composited onto a browser `<canvas>` by `renderMockup()` in `lib/mockup/geometry.ts`; nothing leaves the browser and there is no API route.
- **`/tools/8pc-mockup-generator` — the 8-piece sheet.** Two-stage: a **`react-konva`** live preview in the browser (`sheet-canvas.tsx`, loaded via `next/dynamic` with `ssr: false` — Konva needs a real DOM), then a deterministic server export through `POST /api/mockup-sheet/generate`.
- **`/tools/bag-mockup-grid` — a lineup of bags in a 4-column grid.** Reorderable list (**`@dnd-kit`**), no per-image controls (always auto cover-fit, white background, no labels), exported through `POST /api/bag-mockup-grid/generate`.

Shared rules for the two server-exporting tools:

- **Same request→response, zero-persistence contract as the Cutline Generator.** Both routes are `runtime = "nodejs"` + `force-dynamic`, **no auth and no Supabase**; they take one multipart request (image parts keyed by slot/image id + a JSON `meta` part), compose in memory, and stream the PNG/JPG/PDF straight back. Nothing is uploaded or stored.
- **`meta` is validated with `zod` inside the route** (`lib/*/export-schema.ts`), matching the Server-Action convention. Limits live in `lib/*/limits.ts` (server- *and* client-safe, mirroring `lib/cutline/limits.ts`) so the browser rejects the same files the route would: PNG/JPG/WEBP, 25 MB/file, 80 MB/request, 8 slots (sheet) or 40 images (grid), plus a `MAX_OUTPUT_PIXELS` ceiling on the grid because row count is unbounded. Both routes **sniff magic bytes** (`sniffImageMagic()`) rather than trusting MIME type or extension.
- **Composition is SVG → `sharp` → optionally `pdf-lib`.** One SVG document per output (a `<clipPath>` + pre-resized base64 `<image>` per slot) rasterized in a single `sharp` pass; PDF export wraps that raster. Unlike the Cutline Generator, **no vector path survives into the output** — these are raster mockups, not print-cut files.
- **Geometry is the single source of truth shared by preview and export — never duplicate it.** `lib/mockup-generator/geometry.ts` (`computeDrawRect`, `baseFitSize`) is imported by *both* the Konva preview and `lib/mockup-generator/compose.ts`, so exported pixels match what was previewed. Likewise `lib/mockup/geometry.ts` now **exports** `DIE_PATH` / `CLIP_PATH` / `IMG_RECT` / `DIE_TX` / `DIE_TY` / `Seg` purely so the server-side SVG renderer in `lib/bag-mockup-grid/compose.ts` can draw the identical bag shape that `renderMockup()` draws on canvas — the two renderers exist because Konva/canvas can't run in the route, and they must not drift.
- **The 8-piece template is derived, not hand-listed.** `lib/mockup-generator/templates/eight-piece.ts` builds its 8 slots from one grid (page 1296×756pt, column/row pitch, slot size, corner radius) measured off the reference `8pc-template.pdf` at the repo root. That PDF is a **reference artifact only** — it is never read at runtime, so it needs no `outputFileTracingIncludes` entry.

Nothing derives the step count independently. Insert `{ id, label }` and add a branch in `mylar-printing-wizard.tsx` — that's the whole change.
- **One draft, one owner.** The wizard holds a single `MylarPrintingDraft` plus a step index, so Back and the summary's **Edit** links only move the index — nothing captured later is ever discarded. **No react-hook-form** (unused everywhere else in this repo; see Conventions) and no state library. Scalars mirror into `sessionStorage` so a refresh doesn't wipe five steps; `File` objects never do, but *uploaded* artwork metadata does, since by then the bytes are in Storage and only the key matters. The restore is a post-mount effect on purpose — reading storage during render would desync the server HTML.
- **An order is a set of designs, and the quantity is split between them (`0024`).** A customer ordering 1,000 bags across three designs is three `mylar_designs` rows at 400 / 350 / 250, each owning its own `mylar_artwork_files` (one per `side`) — not a flat pair of artwork columns on the inquiry. The allocation logic is three pure functions in `lib/mylar-printing/types.ts`: `distributeQuantity()` spreads a total evenly and hands the remainder to the earliest designs, `resizeDesigns()` re-splits when the design count changes **while preserving artwork already uploaded to surviving designs**, and `realignDesigns()` re-aligns the split when the ORDER TOTAL itself changes on step 2. `realignDesigns()` exists because the total is editable at any time via Back or a summary Edit link: **one design is always re-synced to the whole order** (there is no other valid value, and the artwork step hides the per-design input in that case, so a stale number would be uncorrectable — this was a hard dead end), while a multi-design split is only redistributed while it is still the generated even one. Once the customer types their own numbers (`draft.designsCustomized`), their split is never overwritten; the ledger asks them to rebalance instead. `totalAllocated()` / `allocationError()` in `schema.ts` are the shared sum and the shared sentence, checked by the Continue gate and re-checked authoritatively by the server. **The sum rule is enforced in application code, not the database** — a cross-row sum is not expressible as a column check, and a trigger would fire mid-insert while the set is still incomplete. `design_number` is stored rather than derived from `created_at`, so "Design 2" means the same design to the customer, the confirmation email, and the admin view.
- **Artwork is direct-to-Storage, per slot, independently.** A *slot* is one side of one design, so an order with three designs has six. `app/actions/mylar-printing.ts` mints a one-shot signed upload URL; the browser `PUT`s the bytes with `XMLHttpRequest` for progress (`lib/mylar-printing/upload-client.ts`). Bytes never touch a Server Action, so the ~4 MB body cap is irrelevant and the limit is the bucket's — **50 MB here, deliberately higher than the 25 MB `client-files`/`design-requests` cap**, because production print sources (layered PSD, flattened TIFF, packaged AI) routinely exceed it. Keep `MAX_ARTWORK_BYTES` (`lib/mylar-printing/artwork.ts`) in sync with the bucket's `file_size_limit` in `0023`. Each slot uploads on its own, so a failed BACK on Design 2 leaves a succeeded FRONT on Design 1 alone and offers **Retry** without re-picking the file.
- **The allowlist is separate from `lib/uploads.ts` on purpose.** Print artwork needs TIFF and doesn't want WEBP/GIF/SVG/ZIP; widening the portal's list to suit this form would widen what admins and portal users can upload too.
- **The inquiry uuid is minted at first upload and becomes the row's primary key** *and* the artwork path prefix. Since `0024` the key is `{inquiryId}/{designId}/{front|back}/{uuid}-{name}`, and the design uuid is minted **in the browser** — which is safe and load-bearing: it is the id the artwork was uploaded under, `verifyArtwork` proves each object actually sits at that prefix, and the same id is then written as the `mylar_designs` primary key, so a forged one can only claim files that do not verify. `isOwnArtworkPath` still accepts the flat `0023` key (`{inquiryId}/{side}/…`) because the wizard mirrors uploaded keys into `sessionStorage` — a customer who uploaded before a deploy and submits after it is holding old-shaped keys, and both shapes are anchored to the same unguessable inquiry uuid. That identity does three jobs: it proves an artwork object belongs to the submission claiming it (a path outside the caller's own prefix is never read *or* deleted), it makes a double-submit idempotent (the second insert hits the PK and returns the reference already issued), and it scopes the discard action. Size and MIME are read back from `storage.info()` at submit time — **the browser's numbers are never trusted**.
- **Public writes go through a validated server action, never an anon RLS policy.** The table has RLS on with no policies (see `0023`), so an anon INSERT grant doesn't exist to abuse. Layers on every submission, in order: zod parse → honeypot + minimum-fill-time → in-process burst limit → durable per-submitter DB limit (a salted, truncated IP hash, same convention as `qr_scans`) → artwork verified against Storage → insert → best-effort orphan cleanup → notification email (failure logged, never loses a stored inquiry).
- **Orphan cleanup is active, not deferred.** Remove, Replace, ticking "I'll send my artwork later", removing a design, **and reducing the design count** all call `discardMylarArtworkAction`, which refuses any path outside the caller's prefix and any inquiry that has already been submitted. A failed insert removes what it just verified. Every wizard-side discard goes through one `releaseArtwork()` helper in the wizard — always from an event handler or effect, **never inside a `setDraft` updater**, which React may invoke twice. It de-dupes by object key (a key is minted once and never reused, which also stops a StrictMode double-invoke reporting a phantom failure) and the action **returns a result rather than `void`**: a failure is logged and surfaced once per batch instead of assumed away. That assumption is exactly how the design-count path leaked silently — `resizeDesigns()` dropped designs past the new count while they still held object keys nothing would ever reference again. **The one gap left is artwork uploaded by someone who then abandons the wizard entirely** — there is no submit to hook, so nothing server-side ever learns about it.

  This is knowingly left as a manual task rather than automated, because every cheaper option was checked and rejected: Supabase Storage has no TTL/expiring objects, and a staging-bucket-then-move scheme would double the failure surface while still orphaning in staging; there is **no Vercel Cron** in this repo (no `vercel.json`/`vercel.ts`) and **`pg_cron` is available but not installed**, so any scheduled sweep would mean standing up new infrastructure plus a recurring production DELETE. The exposure is small — an orphan is at most one 50 MB file in a private, non-enumerable bucket, bounded by how many people upload and then abandon a quote form. Sweep it by hand when it matters; this query lists the candidates (drop the `select`/wrap in a delete once you've eyeballed it):

  ```sql
  select o.name, pg_size_pretty((o.metadata->>'size')::numeric) as size, o.created_at
  from storage.objects o
  where o.bucket_id = 'mylar-artwork'
    and o.created_at < now() - interval '7 days'
    and not exists (select 1 from public.mylar_printing_inquiries i
                    where i.id::text = split_part(o.name, '/', 1));
  ```

  The `{inquiryId}/…` key convention is what makes this a one-liner: an object's first path segment IS the row id it belongs to, so "unclaimed" is a plain `not exists`.
- **Admin side:** `/mylar-requests` and `/mylar-requests/[id]` in the `(app)` group (lucide icons, `PageHeader`/`Table`/`Card`, mobile card list + `sm:` table exactly like `components/invoices/invoices-table.tsx`). Reads run through the service-role client in `lib/mylar-printing/queries.ts` — the cookie-scoped client sees nothing, since there is no `owner_id` to scope to — and every caller re-asserts `requireAdmin()`. The list shows the **real** design count (`getMylarInquiries()` counts `mylar_designs` rows in one extra query and falls back to the stored `design_count` for pre-`0024` rows, annotating the stated figure when the two disagree). The detail page renders an inline thumbnail for artwork whose `previewKind()` is `image` — **raster only**; PDF/AI/PSD/TIFF keep the file card and View/Download, and no document conversion is done anywhere. Contact actions are plain `mailto:` / `tel:` / `sms:` links plus a copy-reference button; the app sends nothing itself and holds no messaging integration. Artwork is served by `app/api/mylar-artwork/[inquiryId]/route.ts`, addressed as `?file=<artworkFileId>` (a side alone no longer identifies a file now that there is one per design) and joined back through `getMylarArtworkFile()` so a valid file id belonging to another inquiry 404s rather than downloading; it mints a 60-second signed URL and **there is no public URL to render**. `getMylarInquiry()` deliberately runs three plain selects instead of one PostgREST embedded select — the embed needs foreign keys in PostgREST's schema cache, which lags a fresh migration and fails with `PGRST200` until it reloads. `/api` is outside the proxy matcher, so that route does its own admin check and must keep doing it.

### Custom design requests (public form + admin intake)

The **second** persisted public form, rebuilt off Formspree onto the Custom Mylar Printing pattern above. Read that section first — the trust boundary, the abuse layers, and the direct-to-Storage upload flow are the same design, and this one literally imports the mylar helpers (`MIN_FILL_MS`, `checkBurst`, `submitterHash`, `SUBMIT_WINDOW_*` from `lib/mylar-printing/abuse.ts`). What follows is only where it differs.

- **One action file is public, one is admin.** `app/actions/design-requests.ts` holds the anonymous path (`mintDesignRequestUploadsAction` → `finalizeDesignRequestUploadsAction` → `submitCustomDesignRequestAction`); `app/actions/custom-design-requests.ts` holds the single `requireAdmin()`-guarded status write. Same split as `mylar-printing` / `mylar-requests`, for the same reason: the public form's bundle must never reference an admin endpoint.
- **Submission order** (`submitCustomDesignRequestAction`): zod parse → honeypot (`website`) + minimum-fill-time → in-process burst limit → durable per-submitter DB count over `submitter_hash` → every asset path matched against `^{requestId}/\d+-…$` → `storage.info()` for authoritative size/MIME (`validateUploadFile` from `lib/uploads.ts`, so this form inherits the **25 MB portal allowlist**, not mylar's 50 MB one) → insert → orphan cleanup on failure → best-effort Resend email to `getAdminEmails()`. A stored request is never lost to a failed email.
- **The reference number is generated, not sequential.** `DES-` + 6 chars from a Crockford-ish alphabet (no `0`/`1`/`I`/`O`), retried up to 5 times against the table's unique constraint — the same collision-retry shape as QR slugs, and unlike invoice numbers, which come from a Postgres sequence. It is what the customer quotes back, so it is shown on the confirmation screen and in the email.
- **`requestId` doubles as the Storage prefix**, exactly like the mylar inquiry uuid: minted in the browser at first upload, verified server-side by the path pattern, then written as the row PK — so a re-submit is idempotent and a forged id can only claim objects that fail `storage.info()`.
- **Admin side:** `/design-requests` and `/design-requests/[id]` in the `(app)` group (lucide icons, `PageHeader`/`Table`, list capped at 200). Reads go through the service-role client in `lib/design-requests/queries.ts` (there is no `owner_id` to scope to) and every caller re-asserts `requireAdmin()`. Files download via `app/api/design-request-assets/[requestId]/route.ts` — addressed `?file=<fileId>`, joined back through `getCustomDesignRequestFile()` so a file id belonging to another request 404s, then a 60-second signed URL; `?inline=1` honors `previewKind()` like the portal route. `/api` is outside the proxy matcher, so that route does its own admin check and must keep doing it.

### Print-partner job portals (private, subdomain-addressed)

A print company's sales rep files design jobs instead of texting them. V1 serves one company, **Zaza**, at `zazaorders.tdstudiosny.com`. Migration `20260825120000_partner_job_portal.sql`; domain model in `lib/partner-jobs/types.ts`.

- **ONE route namespace, three addresses.** The pages live at `app/(partner)/partner/[slug]/{page,login,jobs,jobs/new,jobs/[jobId]}` and are reached by subdomain (`zazaorders.tdstudiosny.com/jobs`), by main-domain alias (`/zaza-orders/jobs`), or directly (`/partner/zaza/jobs`). `resolvePartnerRoute()` in `lib/partner-jobs/routing.ts` is the ONLY place that decides which; `proxy.ts` applies it. **It returns `null` for every other host and path**, which is what makes it safe to run on every request — the main site is untouched. Matching is on the **leftmost hostname label**, so one entry covers production and `zazaorders.localhost:3000` with no environment branching. **Adding a company is a `partner_companies` row + one `PARTNER_SUBDOMAINS` entry + a Vercel domain — never a new route folder**, which is why `[slug]` is dynamic and why the internal path accepts any well-formed slug without a code change.
- **The front door is a 4-digit keypad, and it unlocks auth rather than replacing it.** `app/(partner)/partner/[slug]/access.ts` holds the per-company code (`0420` for Zaza) and, on a match, calls `signInWithPassword` with server-only credentials (`ZAZA_PORTAL_EMAIL`/`ZAZA_PORTAL_PASSWORD`) so the browser ends up with a **real Supabase session**. That choice is the whole point: every RLS policy, storage policy and `create_design_job` call downstream still runs exactly as it would for a per-user login, so the company boundary stays in Postgres instead of moving into application code — which is what dropping the session for a service-role-behind-a-cookie design would have done. It **fails closed** when the env vars are absent, re-checks that the resulting session actually belongs to the requested slug (a mismatch signs straight back out), and throttles wrong codes to 8 per IP per 10 minutes because 4 digits is only 10,000 combinations. The cost, accepted deliberately: **one shared identity per company**, so jobs are attributed to the company, not a person. `partner_users` still models per-rep logins, so reverting is a row plus a password form.
- **The keypad component is the gallery one.** `TasteBudzKeypad` takes the action as a prop; the portals pass their slug through its optional `extraFields` (the only change made to that shared component — default `undefined`, so the four gated galleries are untouched). `enterPartnerCodeAction` normalizes FormData, a bare form POST, and a plain object, so the gate works with JavaScript disabled.
- **Links are rebuilt in EXTERNAL terms, or the address bar leaks the rewrite.** The proxy stamps `x-td-partner-via` (+ `x-td-partner-base` for the alias) on the rewritten request; `partnerBasePath()` (`lib/partner-jobs/context.ts`) reads it and returns `""` on the subdomain, the alias, or `/partner/<slug>`. **Every in-portal href and redirect must go through it.** The proxy deletes both headers from every incoming request before setting them, so they cannot be forged — and forging one would only change link prefixes on a page the caller is already looking at.
- **Redirects are built from the same host the portal was RECOGNISED by.** `redirectWithinHost()` in `proxy.ts` exists because `new URL(path, request.url)` and `x-forwarded-host` can disagree behind a proxy, which would bounce a rep from their subdomain onto the main site's login. Anything that sends a non-partner *away* from the portal (`requirePartnerSession`) makes the target **absolute** via `getSiteUrl()` for the same reason: on the partner host every path resolves back into the portal, so a bare `/dashboard` would 404.
- **What partners may do, in the database.** Reps get SELECT + INSERT + UPDATE + DELETE on jobs/items/files, every verb scoped by `partner_company_id()` — a `SECURITY DEFINER` helper mirroring `portal_client_id()` that checks **both** `active` flags, so deactivating a rep or a whole company revokes everything at once. There is still **no INSERT/UPDATE policy at all on `partner_users`**, so nobody can join or move company.
- **"A rep cannot change job status" is enforced by a TRIGGER, not by the absence of a policy** — this changed in `20260826000000` and is the easiest thing here to get wrong. Until then reps had no UPDATE policy at all, so status was immutable as a side effect. Now that they can edit their own jobs, `protect_design_job_columns()` forces `status`, `company_id`, `job_number`, `submitted_by` and `created_at` back to their previous values for any caller with an `auth.uid()`. It has to be a trigger: RLS `with check` cannot see the OLD row, so "any column except this one" is not expressible as a policy. The service role has no `auth.uid()`, which is exactly how the admin status write still gets through. **Do not "restore" the immutability by removing the UPDATE policy** — that would take the edit feature with it. Note also that the trigger forces back only the five columns it NAMES, which is what makes `partner_done_at` (`20260828000000`) rep-writable with no policy change at all — that is the design, not a gap.
- **These tables have no `owner_id`, deliberately.** A job belongs to the partner COMPANY, not to a TD Studios admin, so `company_id` is the scoping column. Admins therefore read and write through the **service-role client behind `requireAdmin()`** (`lib/partner-jobs/queries.ts`, `app/actions/admin-partner-jobs.ts`) — the anonymous-intake arrangement, which also keeps this migration independent of `workspace_admins` (`20260824193000`): partner admin access works whether or not that has been applied.
- **"Complete" is ONE shared answer, and `status` is it (`20260829180000`).** Both checkboxes — the studio's on `/partner-jobs` and the rep's in the portal — write that same field, so the two views can never disagree. This **reversed** an earlier two-column design (`20260828000000`, `partner_done_at`), which kept the answers apart so neither side could overwrite the other; the studio wanted them in sync instead, and `partner_done_at` is now retired. `isJobDone()` in `lib/partner-jobs/types.ts` is simply `status === "completed"`. **A rep may make only the two moves a checkbox can make** (`-> completed`, `completed -> in_progress`); a trigger reverts anything else, so the `new` vs `in_progress` distinction stays the studio's *without any control having to be hidden* — the enforcement is in Postgres, not in the UI. Un-ticking lands on `in_progress`, never `new` (`JOB_INCOMPLETE_STATUS`). The rep's toggle now emits `job.status_changed` and **is** notifiable: when it wrote a rep-private flag it was deliberately silent, but it now moves the field the studio works from.
- **The admin list is split into two sections, from that same field.** `splitJobsByCompletion()` puts `status === "completed"` under **Complete** and everything else — `new` and `in_progress` together — under **In progress**, which is why a ticked box and the section it sits in can never disagree. Both sections render even when empty (with a one-line note), because a section that vanished would read as a missing feature rather than an empty pile. The admin checkbox lives in its own component (`admin-job-complete-checkbox.tsx`, lucide) rather than sharing the portal's (Phosphor): different icon set, different action, different auth. Both go through **`applyPartnerJobStatus()`** in `app/actions/admin-partner-jobs.ts`, shared with the Status dropdown — not for tidiness, but because that write also revalidates four routes and emits the `job.status_changed` event the studio is notified from, and a second implementation would drift out of step with one of them.
- **The rep's jobs list is TABBED, and the tabs are a partition rather than a set of filters.** `PARTNER_JOB_TABS` is All / New / In Progress / Done, and `partnerJobTab()` returns **exactly one** tab per job — Done wins over the job's status, so the three counts always sum to All and a job is never in two places. Filtering happens **in the server component** off a `?tab=` search param (`parsePartnerJobTab()` coerces anything unknown to All), so a tab is bookmarkable and survives a refresh. The admin list is deliberately **not** tabbed — the studio reads `partner_done_at` as one read-only "Partner marked done" field on `/partner-jobs/[jobId]`, since it is the partner's answer and not a status the studio acts on.
- **Two kinds of control, in two different places, and the split is deliberate.** The status TABS are a *place*: linkable, bookmarkable, resolved server-side in the URL. Search, sort and grid/list are *how you are looking at that place right now*: they live in `JobsBrowser` (`components/partner-jobs/jobs-browser.tsx`), are client-side and instant over the ≤200 rows the page already holds, and push no history entries — nobody wants to share a link to "sorted by name". Sort defaults to **recently updated**, which is only meaningful because `20260829000000` made `updated_at` honest. **Completed jobs always sort last, under every sort option** — `sortPartnerJobs()` makes done-ness the primary key and lets the chosen sort order only *within* each group, because ticking a job off bumps its `updated_at` and would otherwise float the finished work to the top of a queue whose job is showing what is outstanding. It is the same answer the admin list gives by sectioning with `splitJobsByCompletion()`, expressed as a sort key because the tabs above this list already own the "separate places" idea. The chosen VIEW rides in a **cookie** (`PARTNER_JOB_VIEW_COOKIE`), not localStorage, so the server renders the right layout on the first paint instead of flashing a grid and swapping to a list; it is not `httpOnly` because it carries no security meaning at all.
- **The jobs GRID is thumbnail-driven, and the thumbnails are the whole performance story.** Production artwork in `partner-job-files` runs to 4.3 MB a file, so the naive grid downloads hundreds of megabytes. Bytes come from **`/api/partner-job-files/[fileId]?thumb=1`**, which mints a signed URL carrying Supabase Storage's **`transform`** option — a 640px WebP of roughly 55–65 KB, an ~80x reduction on the largest file in the bucket. **No thumbnail table, no generation step, no second bucket and nothing to backfill**, which is exactly why this was chosen over generating thumbnails with `sharp` at upload time (uploads go browser→Storage and never touch a server, so that would have meant a new download-resize-reupload round trip per file). **`next/image` is not an option anywhere in this project** — Vercel's optimizer returns `OPTIMIZED_IMAGE_REQUEST_PAYMENT_REQUIRED` in production — so the grid uses plain `<img>`, the same call `/whiteash` and `/portfolio` already make. Four more limits keep a long page cheap, and none are decorative: `PREVIEWS_PER_JOB` (4) is enforced **server-side** in `summarizeJobFiles()` so a 20-file job can never become 20 requests; only the **first** image of a card is in the DOM until an `IntersectionObserver` says the card has been on screen; the slideshow interval runs **only while the card is visible**, so fifty offscreen cards run zero timers between them; and the redirect itself is browser-cached (`private, max-age=1800`) so scrolling back up re-invokes nothing. **`THUMB_SIGNED_SECONDS` must stay larger than `THUMB_CACHE_SECONDS`** or a replayed redirect lands on an expired token. The **list view loads no images at all**, which is a real reason to keep it. Only raster files qualify (`isPreviewableImage()`); PDF/AI/PSD/EPS and SVG get a placeholder, and the transform endpoint would reject them anyway.
- **Notifications go through an event log, never straight from an action.** The pipeline is `server action → recordPartnerJobEvent() → partner_job_events → dispatchPartnerNotification() → a channel`, and every step is unaware of the ones around it: an action names *what happened* and knows nothing about email; the dispatcher decides *whether* to tell anyone and knows nothing about jobs; a channel decides *how* and knows nothing about either. **No component imports any of it** — `lib/notifications/*` and `lib/partner-jobs/events.ts` are all `server-only`. **ONE EVENT PER USER ACTION, not per row touched**: an edit that adds two files and renames the job is one event whose metadata says so, typed `file.added` > `file.removed` > `job.updated`, because low-level row churn as the unit turns the studio's inbox into noise. `job.done_changed` is logged but deliberately **not** notifiable (`NOTIFIABLE_PARTNER_JOB_EVENTS`) — a rep tidying their own list is not news. **Timing:** the event row is written **inline** (it is the record, and losing it loses the audit trail); the notification is handed to Next's **`after()`**, so a rep filing a job never waits on Resend. Neither can fail the action — everything is caught and logged.
- **Adding SMS is one file plus one line, by construction.** Write `lib/notifications/channels/sms.ts` exporting a `NotificationChannel` (`id`, `isConfigured()`, `send()`), add `sms: smsChannel` to the registry in `channels/index.ts`, and every existing event starts flowing to it for any company whose `partner_notification_settings.sms_enabled` is true. **No migration, no action change, no message-shape change** — `sms_enabled` and `sms_recipients` already exist, the dispatcher already asks for the channel and skips when it is missing, and `renderNotificationSms()` in `lib/notifications/types.ts` is already the rendering. `sms` is absent from the registry rather than stubbed on purpose: a stub that silently succeeds is indistinguishable from a channel that works.
- **Artwork and notes hang off a PRODUCT, not off the job (`20260827000000`).** A job is one 8th bag, one pound bag and one 100ml jar, and the artwork and instructions differ per product; one shared pile of files made the studio guess which file was for which, which is the guessing this portal exists to stop. So `design_job_items` carries `notes`, and every `design_job_files` row carries the `item_id` it is artwork for. **A null `item_id` is a real answer, not a gap** — it means "the job as a whole", which is what every file filed before this migration is — so both job views keep a separate **Job files** card for them, rendered only when some exist, and the form offers that box only on a job that already has one. New jobs get no catch-all box at the bottom at all.
- **Item ids are minted in the BROWSER, and that is load-bearing.** A file is attached to a product before either row exists, so the two halves of a submission have to agree on the id up front — the same reason a mylar design's uuid is minted client-side. Accepting it is safe because it is only ever a claim about the caller's own job: `update_design_job` refuses an id that already belongs to a *different* job of theirs, RLS makes another company's rows invisible, and `create_design_job` refuses a file naming a product that is not on the job being written. **`update_design_job` reconciles the item set by id rather than replacing it** — the original delete-then-insert would cascade every per-product file away the moment a rep fixed a typo. `item_number` is stored rather than derived from `created_at`, so "Item 2" keeps meaning the same product to the rep, the studio, and the notes that reference it.
- **Removing a product removes its artwork — rows by cascade, objects by hand.** `design_job_files.item_id` is `on delete cascade`, so the RPC's item delete takes the file rows with it; Storage objects never cascade, so `updatePartnerJobAction` collects those keys *before* calling the RPC (while the rows are still readable) and deletes them after. Same before/after split as `deletePartnerJobAction`, and missing it is how a private bucket fills with bytes nothing references.
- **`create_design_job` is `SECURITY INVOKER`, and that is the point.** A job, its items and its files are meaningless apart, and PostgREST has no multi-statement transaction — three separate inserts would strand half a submission on failure (the mylar intake lives with exactly that). One function is one transaction, so a rollback leaves nothing but Storage objects. Being INVOKER means the caller's own RLS still authorizes every statement inside, so the function grants nothing: filing a job for another company still fails the insert's `with check`.
- **Job numbers (`ZA-1001`) come from a per-company counter, not a global sequence** — `partner_companies.job_prefix` + `next_job_number`, incremented in a `BEFORE INSERT` trigger. The `update … returning` takes a row lock, so concurrent submissions serialize and get consecutive numbers; `job_number` is `UNIQUE` as the second line of defence. Per-company rather than global is what lets a new company be one row with its own prefix. The trigger **always** assigns, overwriting anything supplied, so a number can never be client-chosen.
- **Uploads are direct-to-Storage under the rep's OWN session**, unlike the mylar/design-request intakes, which must use the service role because their uploader is anonymous. A rep is authenticated, so the `partner-job-files` bucket carries real policies pinning the first path segment (`{companyId}/{jobId}/{uuid}-{name}`) to `partner_company_id()` — Storage refuses a cross-company write independently of the app. 50 MB, matching `mylar-artwork` rather than the 25 MB `client-files` cap, because these are press-ready sources; keep `MAX_PARTNER_UPLOAD_BYTES` in sync with the bucket's `file_size_limit`. **`lib/partner-jobs/uploads.ts` is a third allowlist on purpose** — widening `lib/uploads.ts` to suit this form would widen what admins and portal clients may upload too.
- **Files upload on Submit, not on selection.** The form validates in full *before* the first byte moves (a rep who left the job name blank should not learn that after pushing 80 MB), so "Remove" strands nothing and the only orphan window is a failed insert — which `discardPartnerJobFilesAction` cleans up. That action is the one place the partner side touches the service role, because reps deliberately have no Storage DELETE policy; it is narrowed exactly like `discardMylarArtworkAction` (path must sit under the caller's own prefix, and the job must not exist yet).
- **`/api/partner-job-files/[fileId]` serves two callers with two clients, and the split IS the authorization**: a rep goes through the cookie-scoped client so RLS scopes the row and the signed URL (no company comparison in the route — nothing to drift out of step with the policy); an admin goes through the service role. Anyone else gets 404, never 403. `/api` is outside the proxy matcher, so it authenticates itself and must keep doing so.
- **"Download all" zips in the BROWSER, through that same per-file route** (`components/partner-jobs/download-all-files-button.tsx`, rendered by the shared `JobFileList` so both the partner and admin job pages get it, and only when a job has more than one file). Each file is fetched from `/api/partner-job-files/[fileId]` and the browser follows the 302 to Storage itself, so **no file bytes are proxied through a Vercel function** — a server-side zip route would have pulled up to 20 x 50 MB per click — and **authorization is not re-implemented**: a rep's fetch is RLS-scoped and an admin's uses the service role, exactly as for one file, with no second predicate to drift out of step. It works because Supabase Storage answers with `access-control-allow-origin: *` on the signed-object path, and each fetch mints its own URL so the 60-second expiry applies per file rather than to the batch. Same browser-side `jszip` pattern as the Cutline Generator's "Download All ZIP"; entries are `STORE`d, not deflated, because print sources are already compressed.
- **Admin UI is `/partner-jobs` and `/partner-jobs/[jobId]`, NOT `/admin/partner-jobs`** — the `(app)` group has no `/admin` prefix and every sibling (`/mylar-requests`, `/design-requests`) sits at the root. lucide icons there, Phosphor in the partner portal, per the icon split above.

## Mobile companion app (`mobile/`)

`CLAUDE_SESSION_HANDOFF.md` (repo root) is a newest-first running log of past mobile work sessions. Treat it as history, not current state — e.g. its "Current web state" section still describes the Social Hub, which was removed entirely (`0011_drop_social_hub.sql`). When it conflicts with this file or the migrations, this file wins.

`mobile/` is a **separate, self-contained Expo workspace** — not part of the Next.js build. It is deliberately excluded from the root toolchain (`tsconfig.json` `exclude`, `eslint.config.mjs` ignores, its own `node_modules`), so run all mobile commands from inside `mobile/` with its own deps:

```bash
cd mobile
npm install
cp .env.example .env   # EXPO_PUBLIC_SUPABASE_URL / EXPO_PUBLIC_SUPABASE_ANON_KEY / EXPO_PUBLIC_API_BASE_URL
npx expo start         # then scan QR with Expo Go (iOS), or `npm run ios` for the Simulator
npm run typecheck      # tsc --noEmit
npm run lint           # expo lint
```

- **Stack:** Expo SDK 54 (pinned for Expo Go physical-device testing), React Native 0.81, React 19, **Expo Router** (file-based routes under `mobile/app/`, `typedRoutes` on). Mirrors the web app's two role-based route groups: `(admin)/` and `(portal)/`.
- **Same backend, same RLS, anon key only:** connects to the **same Supabase project** with only the anon key + existing RLS. **No service-role client, no schema changes, no Stripe/Resend.** Never put a service-role key in the mobile app. Every read and write is RLS-scoped to the signed-in user's own access token — the app can only do what that user could do on the web.
- **It is no longer strictly read-only.** Admin/portal browsing is still read-only, but two portal features write or call out:
  - **Native PDF viewer (#4):** `InvoicePdfButton` downloads the authoritative pdf-lib PDF from the web app's existing `/api/invoices/[id]/pdf` route (via `expo-file-system` `downloadAsync`), previews it natively in a WebView, and shares the real file. Auth is the user's Supabase access token sent as `Authorization: Bearer` — the **only** web change this required was making `lib/supabase/server.ts` `createClient()` forward that header to PostgREST when present (a no-op for cookie/browser requests; still RLS-scoped, no service-role). Falls back to a locally rendered HTML invoice (`mobile/src/lib/invoice-html.ts`) when offline or when `EXPO_PUBLIC_API_BASE_URL` is unset. Requires `EXPO_PUBLIC_API_BASE_URL` (the deployed web app URL).
  - **Camera / document uploads (#5):** portal users with `can_upload` upload PDF/JPG/PNG/HEIC (≤ 25 MB) from camera, library, or Files into the existing private `client-files` bucket. **No new upload infrastructure and no schema change** — `mobile/src/lib/uploads.ts` writes straight to Storage + inserts `client_files`/`file_activity` rows exactly like the web `uploadOwnFileAction`, gated entirely by the existing storage + table RLS (`portal_client_id()` + `portal_can_upload()`, uploads-category only). The Storage write uses `expo-file-system` `createUploadTask` against the Storage REST endpoint (bearer = user token, apikey = anon key) to get **upload progress + cancellation**; metadata inserts go through supabase-js. Entry points: portal **Files → Upload** and portal **Invoice → Upload Supporting Document** (`mobile/src/components/upload-document.tsx`).
- **Biometric app lock (#6):** an optional Face ID / Touch ID gate via `expo-local-authentication`, implemented as `BiometricProvider` (`mobile/src/providers/biometric-provider.tsx`) wrapping the navigator *inside* `AuthProvider` in `app/_layout.tsx`. It renders a full-screen lock **overlay** on top of the router, so admin/portal routing is untouched. It only ever gates an **already-authenticated** session — it never blocks first login, and locks on cold start with a persisted session and on return from background (`AppState` "background"). Graceful fallback: if biometrics aren't available/enrolled it fails open and the Settings toggle is disabled with an explanation. The **only** persisted state is a local-only `biometric_lock_enabled` boolean in `expo-secure-store` — **no passwords or tokens are stored.** Toggle lives in both settings screens (`BiometricSettingCard`).
- **Two things share, not duplicate, the web app:** the database types are re-exported from the web app via a relative bridge (`mobile/src/types/database.ts` → `../../../lib/types/database`), so the web schema mirror is the single source of truth. Mobile reads live in `mobile/src/lib/data.ts` (its own copy, parallel to the web `lib/data.ts`).
- **Session persistence** uses `expo-sqlite/localStorage/install` (imported first in `mobile/src/lib/supabase.ts`) as the storage backend, with `processLock` and AppState-driven `startAutoRefresh`/`stopAutoRefresh`. `isSupabaseConfigured` gates the same graceful-degradation pattern as the web app.
- No EAS build / store submission is configured yet (see `mobile/README.md`).
